4. Base image design (tts-base)
4.1 Base image responsibilities
The base image should:

Provide:

Ubuntu (or other Linux) + CUDA runtime that supports Blackwell (use the latest nvidia/cuda:<version>-runtime-ubuntu22.04 or similar that matches your driver & Blackwell GPUs).

System libs used by all TTS stacks: ffmpeg, git, curl, wget, ca-certificates, audio libs, etc.

A fixed Python version and uv binary.

Warm/calculate shared Python build artifacts:

Build wheels for heavy common libs (torch, numpy, scipy, sentencepiece, etc.).

Keep them in a shared cache directory (e.g. /opt/uv-cache) or a wheelhouse.

Drop all compilers/dev packages in the final runtime stage.

Expose:

UV_CACHE_DIR=/opt/uv-cache

Optionally a global wheelhouse: /opt/wheels

Pros:

Heavy packages are compiled only once.

All derived images reuse those layers — much faster builds and smaller incremental changes.

Risks/Cons:

If requirements diverge heavily across TTS engines, your “common” layer might become too fat.

Need a plan for version bumps (pin well; bump deliberately).

4.2 Multi-stage pattern for tts-base
Stage 1 – Builder

Start from nvidia/cuda:<version>-devel-ubuntu22.04
(so you get compilers, headers, etc. needed to build GPU-enabled wheels).

Install:

build-essential, gcc, g++, python3-dev, git, curl, ffmpeg, etc.

Python (if not provided) and uv (download single binary from upstream).

Create a cache dir: /opt/uv-cache.

Run a “warmup” step (pseudo):

export UV_CACHE_DIR=/opt/uv-cache
uv venv /tmp/common-venv
source /tmp/common-venv/bin/activate
uv pip install -r /docker/base/requirements-common.txt
deactivate
rm -rf /tmp/common-venv
This populates /opt/uv-cache with wheels & metadata but discards the venv.

Stage 2 – Runtime

Start from nvidia/cuda:<version>-runtime-ubuntu22.04 (no dev toolchain).

Install only runtime deps:

python3, python3-venv, ffmpeg, git, curl, ca-certificates, libsndfile1, etc.

COPY from builder:

/opt/uv-cache

the uv binary into /usr/local/bin/uv.

Clean APT cache and dev packages.

This final image is tts-base:<tag>.

8. Using uv venv & caches efficiently
8.1 Cache reuse strategy
In tts-base:

Warm the cache with common deps (torch, numpy, etc.).

Set UV_CACHE_DIR=/opt/uv-cache.

In derived images:

FROM tts-base:<tag> ensures they all start with the same /opt/uv-cache.

When uv pip install ... runs in each venv:

It hits the prebuilt wheels in /opt/uv-cache.

No recompilation, just unpack into the venv.

Benefits:

Faster builds for each TTS image.

Strong layer sharing across images.

Risks:

If you change requirements-common.txt frequently, you’ll churn the base cache layer more often.

8.2 Discarding unneeded artifacts
Use a temporary venv in base for warming, then delete it.

In derived images:

Avoid installing build-essential or dev headers at all.

Rely purely on wheels from cache; if something needs building, consider adjusting requirements-common.txt or add a build-only stage.

9. GPU runtime & Blackwell support
Host setup recommendations:

Install NVIDIA driver that supports your Blackwell GPU.

Install nvidia-container-toolkit and configure Docker to use --gpus all or compose equivalent.

Container runtime flags:

docker run --gpus all ... tts-alltalk:latest

In compose:

services:
  alltalk:
    image: tts-alltalk:latest
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: [gpu]
Ensure the CUDA version in your base image matches or is compatible with your GPU driver and Blackwell hardware; if you’re unsure, check NVIDIA’s compatibility matrix and pick the latest stable CUDA runtime image.

11. Alternatives / trade-offs
Single venv per image vs per model

Alternative: one venv per image (Alltalk, Dia, etc.) rather than per model.

Pros: smaller images, simpler entrypoint.

Cons: risk of dependency conflicts; harder to upgrade one model independently.

Prebuilt wheelhouse vs uv cache only

Alternative: expose /opt/wheels wheelhouse and use uv pip install --find-links=/opt/wheels.

Pros: more explicit; can reuse wheelhouse in other contexts.

Cons: extra management overhead vs letting uv manage its cache.

Per-image vs shared base

Alternative: let each image be independent, no base.

Pros: total decoupling.

Cons: huge duplication; slower builds; doesn’t meet your stated goal.

Given your goals (lean runtime images, shared CUDA & Python base, uv everywhere, persistent model cache), the outlined design hits the sweet spot.
